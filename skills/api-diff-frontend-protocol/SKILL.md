# 从 Git Diff 梳理前后端协议文档

## 目标

从后端 git diff 生成给前端、其他 agent、人类工程师直接阅读的协议文档。文档要短，能直接转交前端开工。只描述 HTTP 路径、方法、请求字段、响应 JSON、错误码和字段含义。缓存、消息队列、内部服务调用等与请求响应无关的实现不写进文档。

## 输出文件

- 默认保存到 `~/Documents/`；用户指定目录时以用户为准。
- 文件名必须是：`{business}_年月日.md`，例如 `order-refund_2026年05月25日.md`。
- `{business}` 用本次变更业务名，短横线连接，避免空格。
- 写文件前先列出目标目录；同名文件已存在时不要覆盖，在文件名末尾加 `_2`、`_3` 等序号。
- 最终回复不粘贴整篇文档，只给：文件路径（加了序号就说明原因）、前端必须同步调整的变化、待后端确认项。

## 工作流

1. **锁定 diff 范围**  
   执行用户指定范围。未指定时按顺序选：有未提交改动（含已暂存）用 `git diff HEAD`；否则用当前分支相对主干的 `git diff <主干>...HEAD`，主干按仓库实际的 `main`、`master` 或 `develop` 判断；仍无法确定时先问用户。在文档开头写明本次使用的 diff 范围。在 diff 里找 HTTP 边界，按该仓库实际写法阅读：  
   - 路由声明和入参绑定（装饰器、特性、注解、路由表或框架路由注册）  
   - 请求体、查询参数、响应体的类型定义  
   - 处理函数调用的服务、映射或构造，确认响应体实际赋了哪些字段  
   - 失败返回使用的错误码常量、枚举、固定文案，以及透传上游错误的分支

2. **只输出协议相关项**  
   - **新增**：新路由、新 Body 或 Query 字段。  
   - **变更**：同一 URL 上入参（Body / Query / Header）或响应体形状、字段语义、错误码的变化。  
   - **删除或收紧**：下线的路由、删除的字段、可选变必填、取值范围变窄。这类会让前端原有调用失败，在文首单独列出。  
   - **省略**：纯内部重构、缓存键、消费者、与请求响应无关的单测与工具类（除非直接影响字段名或必填性）。

3. **路由与方法**  
   - 按该仓库的路由声明拼出完整路径，写成 `` `POST /orders/refund` `` 这种形式。路径以 `/` 开头。  
   - 代码里没有写死的全局前缀不要自行补上。  
   - 同一路由分组里本次请求和响应都没变的接口，在文首用同样格式列出，并写明不用改。路由分组按代码的组织方式判断（同一个控制器、蓝图或路由注册块），代码没有分组时按 URL 前缀。

4. **JSON 字段命名**  
   - 请求、响应、嵌套对象、错误对象都使用该接口实际序列化出去的字段名。  
   - 在文档开头用一句话写明本次采用的命名，例如小写开头或蛇形。  
   - 用户明确要求按另一套字段名输出时，以用户要求为准，并在文档开头说明。

5. **响应字段必须结合代码事实**  
   - 类型上声明了的属性，不代表该接口会返回这些字段。  
   - 必须沿处理函数的返回、所调用的服务、映射或构造，追到实际赋值语句再写字段。  
   - 示例 JSON 只写当前返回路径实际构造、前端需要依赖的字段。  
   - 只在类型上存在、当前路径未赋值、默认值、内部补充对象、其他接口复用的字段，不要放进主响应示例。必要时用一句「本接口不依赖该字段」说明。  
   - 条件性字段必须写清条件，例如「仅当 xxx 非空时返回」，并写明不满足条件时是键不存在还是值为 `null`，前端对两者的处理不同。证据不足时省略并标注需后端确认，禁止补字段凑完整。
   - 字段类型、单位、取值追不到时（例如服务层是桩或在其他仓库），示例可以填看起来合理的值，但必须在该字段注释里写「需后端确认」，并汇总到文首的「待后端确认」列表，不能让示例值看起来像已确认的事实。

6. **字段含义写在示例注释里**  
   - 示例使用 `jsonc`。每个需要解释的字段在同一行或紧挨的上一行用 `//` 标明含义、取值和缺省行为。  
   - 文档在第一份示例前写一句：示例里的 `//` 是字段说明，不是请求或响应正文。  
   - 多种特殊场景各写一个小节和一份示例，不要塞进同一个 JSON。场景标题用业务语言，例如「退款并通知」「只取消、不退款」。  
   - 没变的外层字段用一句话带过，示例只展开本次要改的那一块。响应形状没变时，给一份短示例并写明「响应不变」。  
   - 枚举对照、页面互斥可以用短表。不要再为每个字段重复一张「类型 / 必填」大表；只有注释放不下的条件分支才补表。  
   - 面向不熟悉后端代码的人写说明，不写语言或框架的类型名。

7. **成功 / 失败示例必须与代码一致**  
   - 对每个接口，沿处理函数（及必要时调用的服务）列出实际返回分支。  
   - 失败分支使用错误码常量或枚举时，在仓库里查该成员的实际值和文案，写入示例。不编造文案。  
   - 失败分支直接传入文案和错误码时，示例与调用参数一致。  
   - 成功分支写明响应体在 JSON 中的形态（空字符串、`null`、对象、数组），以及外层信封实际有哪些字段。  
   - 信封字段以该接口实际序列化结果为准，例如是否成功、业务数据、错误码、错误文案、时间戳。时间戳若是毫秒级 UTC，注明一句。本次没变、前端也不依赖的信封字段可以不展开。  
   - 写明成功和业务失败时的 HTTP 状态码。很多接口业务失败也返回 200，前端要靠信封里的字段判断，这一点必须说清。
   - 框架或中间件直接返回的失败（缺必填参数、鉴权失败、参数类型错误等）不走业务信封时，能从代码确定返回形态就写出来；确定不了就写进「待后端确认」，不要套用业务信封的示例。
   - 上游错误原样透传时，写明错误码和文案以前端实际收到为准，不伪造具体数字。  
   - 错误场景较多时，用表格列出「条件 → 错误码 → 文案」，避免重复贴大段相同 JSON。

8. **GET 请求**  
   - 不写「Body」；写 **Query** 参数名与必填规则，条件分支以代码为准。  
   - 标题里仍使用完整路由，例如 `` `GET /orders/detail` ``，并在正文写出 `GET /orders/detail?id={id}`。

## 输出结构模板

````markdown
# {业务}接口说明

diff 范围：`git diff main...HEAD`。

新增接口：

- `POST /orders/refund`

修改接口（外层信封不变，只改请求里的某一块）：

- `GET /orders/detail`

前端必须同步调整（删除或收紧）：

- `GET /orders/detail` 不再返回 `legacyStatus`

这些接口不用改：

- `POST /orders/list`

待后端确认：

- 金额单位（元还是分）。
- 缺少 `orderId` 时框架直接返回的格式。

共享约定：HTTP 状态码（例如业务失败也返回 200，以信封字段判断）、编码表、前端负责的限制、保存失败时的行为。

本次 JSON 字段名为实际序列化结果（在这里写明是小写开头、蛇形，或其他）。

示例里的 `//` 是字段说明，不是请求或响应正文。

## 1. 新增 `POST /orders/refund`

这个接口给前端完成什么事。

### 场景名称

场景和变更点，一两句。

```jsonc
{
  "field": "value" // 字段含义、取值、缺省行为
}
```

成功响应。信封字段名换成该接口实际返回的名字，下面只示意结构：

```jsonc
{
  "ok": true, // 是否成功
  "data": {}
}
```

失败时按实际错误码列出。多个错误码用表，不重复贴相同 JSON。

## 2. 修改 `GET /orders/detail`

先写变更点：哪些外层字段不变，前端只改哪一块。

响应不变：

```jsonc
{
  "ok": true,
  "data": true // 保存成功固定为 true
}
```

### 场景名称

这个场景相对旧协议或相对上一场景的差异。

Query：`GET /orders/detail?id={id}`

```jsonc
{
  "changedField": "value" // 字段含义
}
```
````

文首的分组只写本次实际存在的类别，没有的整组删掉。有新增接口时，先按编号写新增，再写修改；没有新增接口时，文首写「没有新增接口」，第 1 节从修改开始。

## 表述要求

- 正文使用简体中文。
- 先写结论和变更点，再给示例。
- 示例值要像真实业务值，但不能伪造固定错误文案或错误码。

## 自检

- [ ] 文件已保存到 `~/Documents/`（或用户指定目录）下的 `{business}_年月日.md`，同名时未覆盖
- [ ] 文首写明 diff 范围，追不到的类型、单位、框架层失败已列进「待后端确认」
- [ ] 写明了成功和业务失败时的 HTTP 状态码
- [ ] 条件字段写明了不满足条件时是键不存在还是 `null`
- [ ] 文首用 `METHOD /完整后端路由` 列出新增、修改、删除或收紧的接口，以及同一路由分组里不用改的接口
- [ ] 每个变更接口先写变更点，再按特殊场景分多个示例
- [ ] 字段含义写在示例的 `//` 注释中，并声明注释不是请求或响应正文
- [ ] 没变的外层字段没有重复展开
- [ ] 每个示例的错误码和文案已在常量、枚举或失败返回处核对
- [ ] 响应示例字段来自实际返回和赋值链，不是类型上的全部属性
- [ ] 已删除未赋值默认字段、内部补充字段、仅其他接口使用的复用字段
- [ ] 字段名与该接口实际序列化结果一致；若按用户要求换了命名，文档开头已说明
- [ ] 未把语言或框架类型名写进给前端的说明
- [ ] 未把缓存、内部队列等写入协议说明
