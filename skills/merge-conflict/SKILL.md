# 合并冲突：先计划，后改文件，不提交

合入用户指定的分支。用户没指定时先问，不要默认某个远程分支。

分两段。第一段只出计划。用户明确说按计划合并之后，才改文件。解决完停住，等人审查。

## 硬约束

- 计划没被确认前，禁止 `git merge`，禁止改冲突文件。
- 解决冲突后禁止 `git commit`、禁止 `git merge --continue`、禁止 push。可以 `git add` 把冲突标成已解决，方便审查 diff。
- 不把某一边整段留下。两边各自要的行为都留下；同一副作用只做一次。
- 没有证据的行为不要编。看不清的调用顺序写进计划，标成待确认，不要猜。

## 第一段：计划

工作区已有未完成合并时，直接读冲突标记。否则用 `git merge-tree` 预览，不要动工作区。

1. 看当前分支、工作区是否干净、是否已在合并中。
2. `git merge-tree --write-tree --name-only HEAD <对方>` 列出真正的内容冲突。退出码非 0 只说明有冲突。
3. 对每个冲突文件，用两边相对 merge-base 的提交说明和 `git merge-file -p --diff3` 抽出冲突块。
4. 自动合并、但两边都改过的相邻文件也要看一眼。本分支独有、且仍被调用的行为如果被静默删掉，写进计划。对方已经删除的整段流程不要加回去。

每个冲突按这个格式写：

```markdown
## 冲突 N：<路径>

两边原因:
- 本分支: <改了什么行为，为什么撞在这里>
- 对方: <改了什么行为，为什么撞在这里>

方案: <留下什么、丢掉什么、顺序为什么这样>

合并后流程:
```
<伪代码>
```
```

伪代码规则：

- 写解决后会执行的步骤，不写冲突标记，不贴大段原代码。
- 用两边真实的函数名、条件、顺序。语言不限。
- 一个冲突一块。同一条路径在多个文件里各写一次时，可以共用一块，并点明哪些文件走这条路径。
- 顺序会改变结果的地方必须写出来。先写再读，和先读再写，伪代码里要分得清。

计划末尾写一句：确认后才开始合并。不要在这一段改文件。

## 第二段：按计划改

用户确认后：

1. `git merge <对方> --no-edit`。已在合并中就接着解。
2. 只按计划改冲突块。自动合并已经合上的导入、依赖和调用不要在解冲突时删掉。
3. 签名因为两边合并变了，就改因此编不过的调用方和测试。这是合并的一部分，不是新需求。
4. 冲突标记清零后再跑受影响的检查。编不过或测试失败就修到和计划一致。对方带进来的、与本次冲突无关的既有错误，记在结果里，不要顺手改掉。
5. 停住。列出改了哪些文件、合并后的关键顺序、检查结果、建议人看的 diff。明确写：未提交，等人审查。

## 审查时交给人的内容

- 冲突文件路径。
- 每条路径合并后的伪代码（与计划一致；执行时若偏离计划，写出偏离原因）。
- 检查命令和结果。没跑的写没跑。
- 未提交。
