# 合并冲突：先计划，后改文件，不提交

合入用户指定的分支。用户没指定时先问，不要默认某个远程分支。

分两段。第一段只出计划。用户明确说按计划合并之后，才改文件。解决完停住，等人审查。

## 硬约束

- 计划没被确认前，禁止 `git merge`，禁止改冲突文件。
- 全程禁止 `git commit`、`git merge --continue`、push。合并必须带 `--no-commit --no-ff`，否则没有冲突时 git 会直接生成合并提交。可以 `git add` 把冲突标成已解决，方便审查 diff。
- 不擅自 stash、reset、checkout 或丢弃工作区改动。
- 不把某一边整段留下。两边各自要的行为都留下；同一副作用只做一次。
- 没有证据的行为不要编。代码和提交说明都看不出的顺序或取舍，可以按语义给推荐做法，但要写明依据并标成待确认，不能当成事实写。
- 需要 RTK 的环境，依赖原始输出或退出码的 git 命令（`status`、`merge-tree`、`merge-file`、`rev-parse` 等）用 `rtk proxy`，避免合并状态被压缩掉。

## 第一段：计划

工作区已有未完成合并时，直接读冲突标记。否则用 `git merge-tree` 预览，不要动工作区。

1. 看当前分支、是否已在合并中（`git rev-parse -q --verify MERGE_HEAD` 有输出即在合并中）、工作区是否干净。有未提交改动时先报告，由用户决定怎么处理，不要自己 stash。
2. 对方是远程分支时，先问是否 `git fetch`，不要默认本地远程引用是最新的。用 `git rev-parse <对方>` 记下对方的提交 SHA，第二段合并这个 SHA。
3. `git merge-tree --write-tree --name-only HEAD <对方SHA>` 列出冲突。退出码 1 表示有冲突。输出第一行是合并结果的 tree OID，接着是冲突文件路径，空行之后是冲突类型说明。需要 Git 2.38+；更旧的版本改用 `git merge-base` 加逐文件比对。
4. 对每个内容冲突文件，看两边相对 merge-base 的提交说明（`git log <base>..HEAD -- <路径>`，对方同理），再取出三份内容抽冲突块。变量后紧跟冒号时必须写成 `${base}:`，zsh 会把 `$base:h`、`$base:u` 这类写法当成修饰符：

   ```bash
   base=$(git merge-base HEAD <对方SHA>)
   dir=$(mktemp -d)
   git show "${base}:<路径>" > "$dir/base"
   git show "HEAD:<路径>" > "$dir/ours"
   git show "<对方SHA>:<路径>" > "$dir/theirs"
   git merge-file -p --diff3 "$dir/ours" "$dir/base" "$dir/theirs"
   ```

   用完删掉这个临时目录。环境限制写入位置时，用 `mktemp -d <允许的目录>/mc.XXXX`。

5. 非内容冲突单独写明处理方式：一边删除一边修改，写清是保留修改还是接受删除，以及依据；重命名冲突写清最终路径；二进制文件只能选一边，写清选哪边、为什么。
6. 两边都改过、但自动合并成功的文件也要看一眼。本分支独有的行为如果被静默删掉，用 `git grep <符号> <第 3 步的 tree OID>` 查它在合并结果里是否仍被调用，仍被调用就写进计划；冲突文件在该 tree 里带冲突标记，其中的调用以冲突块两边的内容为准。对方已经删除的整段流程不要加回去。
7. 函数签名因合并而变化时，查出仓库内的调用方写进计划；仓库内找不到调用方时，写明可能存在仓库外调用方，标成待确认。
8. 这一段发现的、与冲突无关的既有问题（例如缺导入），写进计划的"既有问题"，合并时不顺手修。

每个冲突按这个格式写：

````markdown
## 冲突 N：<路径>

两边原因:
- 本分支: <改了什么行为，为什么撞在这里>
- 对方: <改了什么行为，为什么撞在这里>

方案: <留下什么、丢掉什么、顺序为什么这样>

合并后流程:
```
<伪代码>
```
````

伪代码规则：

- 写解决后会执行的步骤，不写冲突标记，不贴大段原代码。
- 用两边真实的函数名、条件、顺序。语言不限。
- 一个冲突一块。同一条路径在多个文件里各写一次时，可以共用一块，并点明哪些文件走这条路径。
- 顺序会改变结果的地方必须写出来。先写再读，和先读再写，伪代码里要分得清。

没有内容冲突时，不用写冲突块，写一句"预览无冲突"并列出两边各改了哪些文件即可。

计划末尾依次写：

- 待确认项：每项写推荐做法和依据。写明"确认计划即采纳推荐做法，需要改哪项请直接指出"。
- 既有问题（没有就省略）。
- 对方 SHA。
- 一句：确认后才开始合并。

不要在这一段改文件。

## 第二段：按计划改

用户确认后（未单独回答的待确认项按推荐做法执行）：

1. 合并前快速复查：工作区是否仍干净、是否已在合并中；重新 `git rev-parse <对方>`，第一段 fetch 过的远程分支先再 fetch 一次。对方已不是计划里的 SHA 时，先说明差异，等用户决定合并哪个版本。
2. `git merge --no-commit --no-ff <对方SHA>`。已在合并中就接着解。没有出现冲突也停在未提交状态，不要提交。
3. 只按计划改冲突块。自动合并已经合上的导入、依赖和调用不要在解冲突时删掉。
4. 签名因为两边合并变了，就改因此编不过的调用方和测试。这是合并的一部分，不是新需求。
5. 冲突标记清零后再跑受影响的检查。编不过或测试失败就修到和计划一致。没有冲突、也没有签名变化时可以不跑，但要写明没跑；仓库没有可用的构建或测试时写"无可用检查"。检查失败如果来自计划里的既有问题，或对方带进来的、与本次冲突无关的错误，不算偏离计划，记在结果里，不要顺手改掉。
6. 停住。列出改了哪些文件、合并后的关键顺序、检查结果、建议人看的 diff。明确写：未提交，等人审查。

## 审查时交给人的内容

- 合并的对方 SHA 和冲突文件路径。
- 每条路径合并后的伪代码（与计划一致；执行时若偏离计划，写出偏离原因）。没有冲突时写"无冲突"。
- 检查命令和结果。没跑的写没跑。
- 未提交。审查通过后由人执行 `git commit` 完成合并；要放弃就执行 `git merge --abort`。
